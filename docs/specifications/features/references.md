# Feature: References

**Area:** Core agent interface  
**Related:** [orchestrate.md](orchestrate.md), [branching-framework.md §4.4](branching-framework.md)

---

## 1. Summary

A reference is a short token (e.g. `@s2`, `@failingTests`, `@src/pricing.py#apply_discount`) that
stands for content held by the framework rather than by a model's context. Models write references
instead of copying content; the framework resolves them for whoever needs the content.

In orchestrate, references let the planner hand an executor data **the planner never saw**:
"fix the failures listed in `@failingTests`" works even though only the executor that ran the
tests ever held the full output.

---

## 2. Motivation

Without references, the only way to move information between steps is to copy it through the
planner:

1. **Cost.** Every fact the next executor needs has to pass through the planner's context
   twice (once in a report, once in the next `do`).
2. **Loss.** The planner only has the report, a summary. It cannot pass on details it was never shown.
3. **Staleness.** A copied snippet of code goes stale as soon as a step edits that file.
4. **Cold executors.** A new executor re-reads what the previous one already read.

References fix 1–3 directly and reduce 4 (§8).

---

## 3. What can be referenced

| Kind | Example | Content | Live or snapshot |
|------|---------|---------|------------------|
| **Step** | `@s2` | Step 2's instruction and report | Snapshot |
| **Step range** | `@s2..s4` | Steps 2–4, in order | Snapshot |
| **Call** | `@s2.c5` | Result of the 5th tool call in step 2's trace | Snapshot |
| **Named value** | `@failingTests` | A value an executor saved under a name (§6) | Snapshot |
| **Code entity** | `@src/pricing.py#apply_discount` | A file, or a symbol in it | Live |

- **Snapshot** references return what was recorded at the time, labelled with the step it came from.
- **Live** references read current content when resolved. If the content changed since the
  reference was created, the result is marked stale and includes which step changed it
  (known from the framework's change tracking).

---

## 4. Syntax

- A reference is `@` followed by one of the forms in §3, written inline in natural language:
  "Apply the fix decided in `@s2` to `@src/pricing.py#apply_discount`, then run the tests in `@s1.c1`."
- Grammar (`N`, `M`, `K` are positive integers):

  | Form | Meaning |
  |------|---------|
  | `@sN` | step N |
  | `@sN..sM` | steps N–M |
  | `@sN.cK` | call K of step N |
  | `@name` | named value, latest |
  | `@name@sN` | named value as of step N (§7) |
  | `@path` or `@path#Symbol.path` | code entity: a file, or a symbol in it |

- Names are `[A-Za-z_][A-Za-z0-9_]*`; names of the form `s` + digits are reserved for steps.
- Paths are relative to the workspace root (`@src/pricing.py`, never `@pricing.py` for a file in
  `src/`). A token containing `/` or `.` is a path; a root file without either is written `@./Makefile`.
  `#` separates a symbol path (`Class.method`).
- Forms in §9 (e.g. `@s1.c1!`) are proposals, not part of the grammar until adopted.
- **Where references are recognised.** Only in text that passes between planner and executors:
  `do` instructions and executor reports (§6.4). Everywhere else — the final answer to the user,
  tool arguments, file contents, shell commands — `@` is ordinary text and is never resolved.
- **Literal `@`.** Inside instructions and reports, `@` is a reference only at the start of a word
  (so `a@b.com` is plain text), and `@@` writes a literal `@` (`@@s2` is the text `@s2`).
- References are recognised by the framework, not interpreted by the model. An unknown or malformed
  reference is rejected **before** the executor starts, with an error returned to the caller listing
  the valid references, so a typo costs one cheap turn rather than a confused executor.

---

## 5. Resolution

When an executor receives a `do` call whose instruction contains references, each one is resolved in one of two ways.
How each reference was resolved, and the text the executor received, is recorded in the handoff
record ([orchestrate.md §8.4](orchestrate.md)).

### 5.1 Inline

Small content (under a threshold, default ~500 tokens) is expanded into the executor's prompt
directly, below the instruction. Step reports are usually inline.

### 5.2 Handle

Larger content is **not** expanded. The executor sees a one-line handle with a summary:

```
@s1.c1 — step 1, bash `npm test`, 4.2k tokens: exit 1, 3 of 48 tests failed
```

The summary comes from:

| Kind | Summary source |
|------|----------------|
| Step | First line of the step's report |
| Call | Generated by the framework from the tool name, arguments and outcome (exit code, item count, thrown error) — no model call |
| Named value | Written by the executor when saving (§6.2); if missing, type and size only |
| Code entity | Symbol kind and signature, or file outline size |

and fetches what it needs with `resolve`, which can return a slice instead of the whole value:

```ts
await tools.resolve({ ref: "@s1.c1", grep: "FAIL" });
await tools.resolve({ ref: "@s1.c1", lines: [120, 180] });
await tools.resolve({ ref: "@src/pricing.py#apply_discount" });   // just that function
```

`ref` is a handle token (`"@s1.c1"`) or a live-ref object stored in state (branching-framework
§4.4); the result is `{ text, stale }` in both cases.

`resolve` is always available to executors and is not subject to tool selection.

### 5.3 Transitive references

Content that itself contains references (a report mentioning `@failingTests`) is resolved one level
deep only; nested references stay as handles.

## 6. Producing references

### 6.1 Automatic

Every step and every tool call in every step gets a reference, with no action from any model.
Executor traces are kept for the lifetime of the task (not shown to anyone unless resolved).

### 6.2 Named by the executor

Executors name values worth keeping by writing them to branch `state`
([branching-framework.md §4.4](branching-framework.md)). In orchestrate, `state` is
**task-scoped** and shared by all executors: each key is a named reference.

```ts
state.failingTests = failures;                   // snapshot → @failingTests
state.discountFn = await tools.refSymbol({ file: "src/pricing.py", name: "apply_discount" });
                                                  // live → resolves to the current function
```

To attach a summary (§5.2), save through `save`, which writes the same `state` key:

```ts
await tools.save({ name: "failingTests", value: failures,
                   summary: "3 failing tests in test_pricing.py, all off-by-tax" });
```

The report footer lists names created or changed in that step, with their summaries:

```
Saved: @failingTests — 3 failing tests in test_pricing.py, all off-by-tax
       @discountFn — live, pricing.py#apply_discount(order, rate)
```

This is how the planner learns that references exist. The planner only sees step references,
named references, and code entities it has been told about; call references (`@s2.c5`) are
mainly for executors and hot paths, since the planner never saw the calls.

### 6.3 By the planner

The planner can reference any step, any name in any footer, and any path or symbol mentioned in a
report. It cannot create references itself; it has no content to store.
It can read a reference with its own capped `resolve`
([orchestrate.md §4.1](orchestrate.md)) when a summary is not enough; most of the time the
footer summary is.

### 6.4 References in reports

Executors may write references in their reports ("full output in `@s3.c2`"). Every reference in a
report must resolve. Before the report is returned, the framework checks them; if any fail, the
executor gets the error and one more turn to fix the report. References still invalid after that
are replaced with `[invalid ref: …]` so the planner never receives a dangling one.

---

## 7. Lifetime and limits

- References live for one task. A new task starts with an empty store.
- Snapshots are immutable. Named values can be overwritten by a later step; the old value stays
  reachable as `@name@s2` (the value as of step 2) for the rest of the task.
- The store has a size cap per task; if exceeded, the oldest unnamed call results are dropped
  first, and resolving them returns a clear "expired" error.

---

## 8. Reducing re-read cost

References remove the need to *copy* content, but a cold executor still has to *read* what it is
pointed at. Two things keep that cheap:

1. **Live code references to the smallest unit.** `@src/pricing.py#apply_discount` resolves to one
   function, not the 600-line file.
2. **Structure-aware tools.** For files with structure (source code, JSON/YAML, Markdown), tools
   that return an outline and read one unit at a time let an executor take only what it needs. These are catalog tools, not part of this spec, but
   references rely on them to be worthwhile: `outline` (symbols, Markdown headings, JSON/YAML
   keys, each with a line range) and `readSymbol` for one code symbol; a Markdown section or a
   key is read by its line range.

Unstructured content (logs, prose) falls back to slicing with `grep`/`lines` (§5.2).

---

## 9. Open questions

Questions 1 and 2 are **deferred**. The defaults in this spec apply until run data (inline vs.
`resolve` token cost, how often planners reference steps vs. named values) shows a need to change them.

1. **Inline threshold** (deferred; default: fixed ~500 tokens, §5.1). Content under the threshold
   is pasted into the executor's prompt; larger content becomes a handle fetched with `resolve`.
   Alternatives: a threshold per kind (e.g. always inline step reports), or letting the planner
   force inline with `@s1.c1!`.
2. **Planner-visible call refs** (deferred; default: not listed, §6.2). Every tool call inside a
   step gets a reference (`@s2.c3` = step 2, call 3), but the planner only learns about steps and
   named values. Alternative: reports list notable calls (`@s2.c3: test run`) so the planner can
   point a later step at them, at a few tokens per call, instead of relying on executors to name
   everything worth keeping.
3. **Cross-task references.** Out of scope for now; would need a persistent store and a way to
   detect that the workspace changed between tasks.
