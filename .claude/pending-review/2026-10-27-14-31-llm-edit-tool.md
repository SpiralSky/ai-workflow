# tools: llmEdit — LLM-powered file edit tool

**Date:** 2026-10-27  
**Step:** post-step-7 analysis (orchestrate do-call cost analysis)  
**Status:** pending

---

## What happened

Orchestrate write do calls cost 3–4 secondary turns each: the executor re-reads the file,
then edits (sometimes failing and needing a recovery turn). The executor's re-read is a
structural problem: it starts with no file content, so it must read before it can edit.
Even with reference passing from the planner, the executor still needs to dereference and
build the edit plan in its own context, which takes turns.

A `llmEdit` tool would eliminate the re-read entirely: the tool itself fetches the file,
passes it + the edit instruction to a cheap small model, and returns the modified content.
The executor calls it in one branch call and never needs the file in its own context.

## Decision needed

Should `llmEdit(path, instruction)` be added as a new tool in the L (or new) catalog?

## Options considered

1. **Add `llmEdit` tool** — `llmEdit({ path, instruction })` fetches the file, calls a
   configurable small model (e.g. 8B), returns `{ content, summary }`. The executor writes
   back with `writeFile`/`edit`.
   - Pro: executor write do call becomes 1–2 branch turns (call llmEdit → write); no re-read;
     cheap model does the mechanical edit; works even when executor has no file context
   - Con: adds an LLM call per edit; requires model configuration and cost tracking for the
     inner call; small model may fail on complex multi-hunk edits; adds a new tool category

2. **Do not add; rely on reference passing** — planner passes `@path` reference; executor
   dereferences without re-reading. See pending-review `2026-10-27-14-30-orchestrate-dispatch-efficiency.md`.
   - Pro: no new tool needed
   - Con: executor still needs turns to reason about the edit; doesn't help with recovery turns

3. **Add `llmEdit` as a future tool (post-eval)** — note the idea in tools.md, defer until
   the eval shows it's needed at L-catalog scale or on harder problems.

## Recommendation

Option 3 for now — the current problems are small enough that reference passing (option 2 in
the other pending-review) likely closes most of the gap. `llmEdit` becomes more compelling on
larger codebases where a single function is buried in a large file, or when the edit requires
reasoning across multiple locations. Worth speccing once L-catalog eval results are in.
